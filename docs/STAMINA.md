## スタミナ（学級ポータルの一部として動く から移した）

- **スタミナの たまり方（2026-10-25〜、サーバの `_sanmon_stamina`。SQL は `supabase-sql/2026-10-25-sanmon-stamina.sql`）**：
  単元アプリの正解1問 +1（ペア 0.5）。**1つの項目で1日5まで・もう熟達した項目（5問れんぞく正解のあと）は半分。1日の上限（前は30）はなし**。
  がんばりボーナス：実力の階段の新しい段 +3・はじめての熟達 +2（本番テストは下の「点数ぶん」に変えた）。ためられるのは100まで。前の日までは前のきまりのまま。
  **たまる・使うは時刻の順に数える**（2026-11-09 バグ直し。`supabase-sql/2026-11-09-sanmon-stamina-chronological.sql`）：前は1日ぶんまとめて「足して100で切る→その日に使った分を引く」だったので、使いきったあとに解いたぶんが消えていた。
  **町のスタミナ（2026-11-09 13:39〜 先生と決めた。SQL は `supabase-sql/2026-11-09-sanmon-town-stamina.sql`、サーバの `_sanmon_pools`）**：単元アプリの正解でたまる分は、その単元の町の「町のスタミナ」（町ごとに50まで）。
  がんばりボーナスは「共通スタミナ」（100まで。切りかえ前にたまっていた分も共通）。ぼうけんのバトルは 町 → 共通 の順に使う（`AdventureMode` の `startBattle` が reason に「@町の key」を付ける。key は kit の `sanmonTownKeyOf(town.unit)`）。
  スピード・モンスター対戦・クラス対戦は共通だけ（アプリの無い町は 2026-11-11 から町のスタミナあり。下に書いた）。わり算の筆算は 筆算の項目（hissan-?-1／?-2・?-3）で ÷1けた・÷2けたに分け、ほかの項目は2つの町の共有。小数は アプリの項目のまとまりで しくみ／かけ算わり算に分ける（表 `sanmon_skill_town`）。
  **本番テストは点数ぶん**（2026-11-10 17:30〜 先生と決めた。SQL は `supabase-sql/2026-11-10-sanmon-test-points.sql`）：点数の割合×10（切り捨て）を、そのテストの単元の**町のスタミナ**へ（町の無いテスト・SANMON の本番テストは共通）。
  受けるたびにもらえる・同じテストは1日3回まで・DUO は0。簡単なテストばかり受けても、その町にしかたまらないようにするため。前の「8割合格 +5（共通）」は切りかえ前の分だけ数える。
  **スタミナの釣り合い**（2026-11-10 23:15〜 先生と決めた。SQL は `supabase-sql/2026-11-10-sanmon-balance.sql`）：1分あたりのスタミナを、練習・本番テスト・実力の階段で だいたい そろえる（どれも1分に2〜3。マッチング法則）。
  **小4算数のアプリ（apps の grade=4・subject='算数'）と SANMON だけ**（国語・英語・5〜6年は 正解・熟達・階段とも0）。
  本番テストは テストの大きさに合わせる：ぜんぶ（150点）で満点の割合×20、表だけ・裏だけは その分（`_sanmon_test_full`。倍の見方は100点で1枚）。同じテスト（表・裏・ぜんぶは別）の その日1回目は満額・2〜3回目は半分・4回目から0。
  SANMON の本番テストも テストの名前の番号で町を決める（`_sanmon_test_pool`：3→わり算・4→がい数・5→小数・6→分数。大きい数・折れ線・まとめは共通で その日1回目だけ）。
  実力の階段（極限）は その回に のぼった段×3 を その単元の町へ（アプリごとに その日1回目は満額・2回目は半分）。はじめての段 +3・はじめての熟達 +2 は共通のまま。
  **アプリの無い町（大きい数・折れ線グラフ・角）にも町のスタミナ**（2026-11-11 10:50〜 先生と決めた。SQL は `supabase-sql/2026-11-11-sanmon-noapp-towns.sql`）：SANMON の れんしゅう・ふくしゅう の正解（learning_event の module_id＝町の key、label が「れんしゅう：」「ふくしゅう：」）を その町へ（アプリと同じ数え方）。
  バトル・デュエルの中の答えは数えない（バトルでスタミナが戻らないように）。SANMON の本番テスト「1. 大きい数」「2. 折れ線グラフ」も その町へ。画面は「サーバが towns を返す町」に町のスタミナを出す（`key in stamina.towns`）。
  **バトル1回のスタミナは町の達成度で安くなる**（2026-11-11 先生と決めた。SQL は `supabase-sql/2026-11-11-sanmon-town-cost.sql`）：達成度＝その町の単元の練習の項目のうち熟達（5れんぞくノーミス）した割合。100％→2・75％以上→3・50％以上→4・それより下→5。アプリの無い町・スピード・対戦は5。
  決めるのはサーバ（`sanmon_spend` が `_sanmon_town_cost` で計算。送られた数は使わない）。画面の「1回 n」は kit の `sanmonBattleCost`（同じ項目＝kit のカタログ・同じ熟達。2026-11-16 に SANMON の `utils/townCost.ts` の写しから置きかえた）。
  **アプリの無い町（大きい数・折れ線グラフ・角）は 1回 3**（2026-11-12 先生と決めた。前は 5。SQL は `supabase-sql/2026-11-12-sanmon-noapp-town-cost.sql`、画面は kit の `SANMON_RULES.noAppTownCost`）。
  **kit のカタログ（項目）を変えたら、サーバの表 `sanmon_town_skill` を作り直す**（`node scripts/export-town-skills.mjs` の行で）。
  わり算の筆算の2つの町（÷1けた・÷2けた）は、練習の条件も達成度も**同じ32項目**で数える（同じ条件で いっしょに開く）。筆算シミュレーターの5項目（hissan-2-1〜3-3）は 2026-11-11 に足した（kit 0.34.1。前はカタログに無く、筆算そのものが数えられていなかった。SQL は `supabase-sql/2026-11-11-sanmon-hissan-core-skills.sql`）。
  画面は**文字で**出す（2026-11-10）：ぼうけんの左上に「スタミナ／この町 n/50 ・ 共通 n/100／▶ バトル あと n回（1回 5）」、マップの町ごとに「町のスタミナ n/50」、
  メニューの帯に「スタミナ 共通 n/100」と「共通だけで バトル あと n回」、ひらくと町ごと（`PortalStatusBar`）。
  かんたんな項目の周回では たまりにくく、いろいろな項目・苦手・テスト・階段で よく たまる。kit の `SANMON_RULES.dailyCap` は もう使っていない（子ども用ハブの説明が「30まで」なら 全体セッションで直す）。

- **スタミナの計算は「変わったときだけ」**（2026-11-19。SQL は `supabase-sql/2026-11-19-sanmon-pools-cache.sql`）：授業中に `sanmon_status`・`sanmon_spend`・クラス対戦の へや作りが
  3秒（子どもの端末＝anon の打ち切り）を超えて 数百回 失敗していた（ジムリーダーに挑むと「読み込みエラー」・スタミナが ふえないように見えた）。
  `_sanmon_pools` は 結果を表 `sanmon_pools_cache` に のこし、記録（learning_event・test_result・trial_result・sanmon_spend・skill_state）が 変わったときだけ（トリガーで `ver` +1）・日が かわったときだけ 数えなおす。
  **数え方の本体は `_sanmon_pools_fold`（2026-11-20〜。前は `_sanmon_pools_compute` に直接 書いてあった）。きまりを変えるときは こちらを直す**（直したら `update public.sanmon_pools_cache set done_ver = -1; update public.sanmon_pools_snap set ver = ver + 1;` で全員 数えなおす）。
  数え方に使う表を 新しく足したら、その表にも トリガー `sanmon_bump_*`（`_sanmon_bump_ver`）を付ける（付けないと、のこした古い数が出る）。
  クラス対戦は `_duel_cost()` が 0 のあいだ スタミナを数えない。
  **子どもの問い合わせの中では 数えなおさない**（同じ日の2つめ。SQL は `supabase-sql/2026-11-19-sanmon-pools-fastpath.sql`）：授業中は 答えるたびに記録がふえ、毎回の数えなおしが 3秒を こえて 9割が失敗したため。
  `_sanmon_pools` は「最後に数えた数 − そのあと使った分（`_sanmon_pools_minus_spends`）」をすぐ返す（使いすぎには ならない）。**そのあと たまった分は 2分ごとの裏の仕事（`refresh_sanmon_status_cache`・cron `sanmon-status-cache` `*/2`）で 入る**（最大2分ほど おくれて出る）。
  `sanmon_status` は のこした状態（町の判定の材料）に スタミナだけ 入れかえて返す。本体は `_sanmon_status_compute`（もとの `sanmon_status`）。裏の仕事は さいきん記録が ふえた子から、1回40秒まで。
- **スタミナの台帳化**（2026-11-20。SQL は `supabase-sql/2026-11-20-sanmon-pools-ledger.sql`）：1年ぶんを毎回 数えなおすと 記録がふえるほど重くなる（11月で 1人 最大0.35秒。スタミナ道場で さらに ふえる）。
  `_sanmon_pools_fold(子, はじめ, おわり, はじめの状態)` は、ある時刻から ある時刻までの記録を「はじめの状態」から数える（数え方は前と同じ）。
  `_sanmon_pools_compute` は、きょうの0時までの状態（スタミナ・町ごとの数・項目ごとの熟達した時刻／つづけて正解の数・実力の階段の最高の段）を 表 `sanmon_pools_snap` に1日1回のこし、きょうの記録だけを足す（1人 平均2ミリ秒）。
  きょうより前の記録が あとから届いた・消された・直された（トリガー `_sanmon_bump_ver`）／`apps`・`sanmon_skill_town` が変わった（`_sanmon_bump_all`）ときは、のこした状態を古くして（`ver` +1）次に 0時までを数えなおす。
  たしかめ用に、1年ぶんを一度に数える `_sanmon_pools_full` がある（きまりを変えたら、全員 `_sanmon_pools_full` と `_sanmon_pools_compute` が同じになることを確かめる。SQL の いちばん下）。
  **同じ時刻の記録は `event_id` の順にならべる**（SANMON は 1回の答えで 同じ時刻の記録を2つ送ることがあり、前は 熟達の判定が 数えるたびに変わることがあった）。
- **スタミナ道場**（2026-11-20 先生と決めた。SQL は `supabase-sql/2026-11-20-sanmon-dojo.sql`）：ぼうけんの各町の広場（ショップの東）に「スタミナ道場」。
  単元アプリへ行かなくても、**その町の単元アプリと同じ問題・同じ解答画面**（`apps/<app>/` の写し）で れんしゅう（じぶんで えらぶ／おまかせ）・ふくしゅう ができる。本番テストは あとから1本ずつ足す。
  - **記録は単元アプリで解いたのと同じ**：解答画面が作る記録（`useRoundRecorder` → `apps/_shims/progressStore` の `recordResult`）を、道場が開いているあいだだけ `setDojoSink` で受け取り、
    `services/dojo.ts` が 単元アプリの progressStore と同じ数え方（5問れんぞくノーミスで熟達・とちゅうでやめた記録は熟達とふくしゅうを動かさない・kit の `scheduleAfterResult`）で端末に持ち、
    kit の `createSyncedStorage({ appId: その単元アプリ })` で送る（learning_event・skill_state）。サーバから見ると「その子の もう1台の端末」。PRISM・SOL・町の解放・スタミナは 単元アプリで解いたときと同じになる。
    はじめて道場で解く項目は、サーバの記録（`my_skill_state`）の「つづけて正解」「ふくしゅうの予定」から つづける（試行の数は足さない＝PRISM で二重に数えない）。
  - **スタミナの数え方は変えない**（1日1項目5まで・熟達後は半分・町50まで）。画面の「きょう あと いくつ」はサーバの `sanmon_dojo_today`（項目ごとの きょうの分と熟達）から。
    解いた分は サーバが数えなおすまで（2分ほど）「さっき +N」として画面の中だけで足して見せる。
  - **SOL の ふくしゅうの予定**（サーバの `my_skill_state`）は「いちばん最近に解いた端末」の予定を使う（前は端末ごとの いちばん早い予定で、道場で復習しても 単元アプリの古い予定が のこった）。
  - 名乗っていないとき（おためし・デモ・体験）は使えない。アプリの無い町（大きい数・折れ線グラフ・角）では「SANMON の れんしゅう・ふくしゅうで たまる」と案内するだけ。ぼうけんが閉じていれば 道場にも入れない。
  - レベルの名前と記録の名前がちがう項目（エラーハンターの `eh-judge`／`eh-fix`、小数の たし算ひき算の `addsub-*` など）は `services/dojo.ts` の `OVERRIDES`。解いたときに実際に付いた名前も覚えて（`bm_dojo_learned_skills`）、「きょう あと いくつ」に使う。
  - **読みこみを軽くしてある**（2026-11-20）：解答画面は `apps/registryLoaders.ts` で **アプリごと**に読みこむ（前は10アプリぶん＝圧縮して約280KBを一度に読んでいた）。`services/appRounds.ts` が使いまわし、町に入って少しあとに その町のぶんを先読みする（`prefetchDojo`）。
    道場の一覧は サーバの返事（きょうの分・じぶんの記録）を待たずに出し、数は「…」→ 届いたら入れる。メニュー・道場を開いているあいだは 後ろの3Dの描画を止める（`FieldScene` の `paused`。弱い端末で問題の表示をじゃましていた）。
    弱い回線＋4倍おそいCPUで 測って、台詞のあと一覧が出るまで 約5秒→約2秒、問題が出るまで 約3秒→約0.3秒、開くときの通信 約1MB→約16KB。アプリを足したら `registryLoaders.ts` にも足す（`npm run check` の `verify-app-rounds` が registry.ts との一覧のずれを止める）。
  - **本番テスト**（2026-11-20）：道場の「ほんばんテスト」タブで、その町の単元アプリの本番テスト（`MockTestModule`＋`testConfig` の写し）をそのまま解ける。10アプリ・12町。
    記録は 単元アプリと同じ（`app_id`＝その単元アプリ・`skill_id`＝`mock-test`（小数のかけ算とわり算は `mock-test-muldiv`）・点数の詳細つき）で、スタミナ・町の解放（8割の日が3日）・PRISM の本番テストの数に そのまま入る。
    定義は `apps/<app>/sanmonTest.tsx`（`AppTestDef`）、読みこみ口は `apps/registryLoaders.ts` の `APP_TEST_LOADERS`（れんしゅうの解答画面と別のかたまり）。
    アプリの外枠・設定・ふりかえりの保存は代わりの部品（`apps/kawari/constants.ts`・`apps/suihei/constants.ts`・`apps/syousu/store/reflectionStore.ts` など。`apps/manifest.json` の shims）。小数は 1つの画面の中で2つのテストから選ぶ作りなので、どちらの町からも同じ入口になる。
    新しい単元アプリの本番テストを足すときは、manifest に `lib/testConfig.ts`・`components/modules/MockTestModule.tsx` を足して写し、`sanmonTest.tsx` と `APP_TEST_LOADERS` に足す（`npm run check` の `verify-app-rounds` が、読みこみ口が無いと止める）。
  - 開発サーバ（StrictMode）では kit の `useRoundRecorder` が記録を残さない。記録の確かめは StrictMode を外すか 本番と同じビルドで。
- 子どもむけのスタミナの説明はメニューの帯をひらいたところ（`PortalStatusBar`）。見出し＋短い1行で書く（2026-11-11）。きまりを変えたら ここも直す。
